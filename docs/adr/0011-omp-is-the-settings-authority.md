# omp is the Settings authority; the app never keeps a copy

**Status:** accepted

The settings page reads and writes omp's configuration exclusively through the omp CLI (`omp config list --json` / `set` / `reset`), invoked from the Rust shell as named, specta-typed bridge commands — the same lever `browser.relay` already uses. The app holds no settings store of its own: values are always whatever the binary reports, edits are always validated by omp's schema, and a change takes effect for sessions started afterwards (omp has no hot-reload and rpc-ui has no settings channel, so this is the truth of the system, not a choice).

Because `omp config list --json` emits values but not structure (tabs, groups, labels, options, conditions), omp gains an upstream `omp config schema --json` command that makes the running binary describe its own settings surface, and a real `omp config unset` — both landed in `can1357/oh-my-pi` and pulled in through the normal pin bump before the omp-backed sections ship. Visibility conditions cross that boundary declaratively (`{ dependsOn, equals }` for setting-dependent ones, a platform tag, a terminal-capability marker) and are evaluated live in the app against the values the binary reports, never baked in. Two alternatives were rejected: importing omp's `SETTINGS_SCHEMA` into the renderer — its first import is `@oh-my-pi/pi-ai`, a value barrel over `node:crypto`/`node:fs`/`node:tls`/`bun:sqlite` modules that cannot live in a Tauri webview — and a build-time descriptor generated at pin-bump, which needs a Bun runtime this toolchain does not have and would be a second copy that drifts. The binary's list stays authoritative for *what exists*; a binary that lacks `schema` (an older override) degrades to an Advanced-only rendering from `list --json`'s type and description, never a blank page. A key claimed by a bespoke section (the Models picker owns `enabledModels`, `disabledProviders`, `modelRoles`; the approval, fallback-chain and provider-limit editors own their records) is excluded from generic rendering and its Advanced row becomes a pointer to that section, so no key ever has two editors.

Scope is global-only (`~/.omp/agent/config.yml`). omp discovers a project layer at `<cwd>/.omp/config.yml`, `<cwd>/.omp/settings.json` and `<cwd>/.claude/settings.json`, so every `omp config` invocation runs with `cwd` set to a guaranteed-empty scratch directory — never the user's home, where `~/.claude/settings.json` would be merged in as a "project" and beat the global values the page is editing. Until `omp config unset` is in the pinned binary, `reset` writes today's default as an explicit value; the page labels that action by what it does ("Set to current default") and derives its modified indicator by comparing against the schema default.

Four values structurally cannot live in omp — which omp binary to run (you must choose the binary before you can ask it anything), Chromium path, default working directory, and the app's own theme — and omp rejects unknown keys. These are *App Preferences* (see `gui/CONTEXT.md`): a tiny versioned JSON file owned by the Rust shell, unknown keys preserved verbatim on write, readable with zero dependency on a working omp. The settings page must open and let the user repair the omp-path override even when every omp-backed section has failed; that override remains gated by ADR-0004's smoke test and acknowledgement.

A GUI-owned settings file mirroring omp's config was rejected: it is a second source of truth for values the user also edits from the terminal, and every pin bump would widen the gap.
